## Public send API

- [ ] **SendGrid-compatible send endpoint.** Add `POST /api/v3/mail/send` that accepts the SendGrid v3 mail-send payload so existing SendGrid client libraries work by pointing their base URL at this backend (`@sendgrid/client`: `setDefaultRequest('baseUrl', …)`, Python SDK: `host=`; verify per library). Reuse the existing API key auth (`Authorization: Bearer <key>`, same as SendGrid) and translate the payload in a new DTO onto `PublicSendService.send`. Mirror SendGrid's response: `202` with an empty body and the message id in the `X-Message-Id` header; validation errors as `400` with SendGrid's `{ errors: [{ message, field }] }` shape. Initial subset: `personalizations[].to` (plus `cc`/`bcc` once multiple recipients are supported; today `PublicSendDto` takes a single `to`), `from: { email, name }` (needs display-name support), `reply_to`, `subject`, `content[]` (`text/plain` → `text`, `text/html` → `html`). Reject unsupported fields (`attachments`, `template_id`, `dynamic_template_data`, `send_at`, `categories`, …) explicitly with `400` instead of silently ignoring them. SES compatibility is out of scope for now: SigV4 needs the plaintext secret, but API keys are stored hashed.

## Deliverability

- [ ] **Blocklist / IP reputation checks.** Periodically check the sending server's public addresses (`MAIL_SERVER_IPV4`, `MAIL_SERVER_IPV6`) against DNS-based blocklists and show the result in the admin UI (e.g. on the settings page next to the read-only IPs), so an operator notices a listing before bounces pile up. Lookups are plain DNS queries of the reversed address under the list's zone (`4.3.2.1.zen.spamhaus.org`, nibble format for IPv6); `NXDOMAIN` means not listed, a `127.0.0.x` answer means listed, with the return code naming the sub-list. Candidate lists: Spamhaus ZEN (SBL/XBL/PBL/CSS), SpamCop (`bl.spamcop.net`), Barracuda (`b.barracudacentral.org`, needs a free registration of the querying resolver), Mailspike, PSBL, UCEPROTECT; optionally the domain lists Spamhaus DBL and SURBL/URIBL for `MAIL_HOSTNAME` and the sender domains. Make the list set configurable rather than hard-coded. Caveats: Spamhaus refuses queries arriving via public/open resolvers (Google, Cloudflare, …) and answers with `127.255.255.x` error codes, which must be reported as "check failed", not "listed"; heavier or commercial use needs a Spamhaus DQS key (optional env, then query `<key>.zen.dq.spamhaus.net`). Most lists don't support IPv6 yet. Run it as an `@Interval` job with `@OnOneInstance({ key: 'deliverability:blocklist-check' })` and `@WithoutOverlapping()`, at a low rate (hours, not minutes), store the last result per list, and document it plus any new env vars in `apps/docs` (and the roadmap page while it is only planned).

## Mailing lists

- [ ] **Mailing lists.** Let a project manage lists of subscribers and send one mail (a template) to every subscriber of a list. Needs: list and subscriber models (address, status `pending`/`subscribed`/`unsubscribed`/`bounced`, consent timestamp), import/export, and subscribing via an inbound form or the API with double opt-in (confirmation mail with a signed token) for GDPR. Every list mail carries `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058) pointing at a public unsubscribe endpoint, which Gmail and Yahoo require from bulk senders, plus a per-recipient unsubscribe link usable in the template. Hard bounces and complaints must suppress the address automatically, which depends on linking bounces to the mail that caused them (VERP, see the roadmap). Send through a BullMQ queue, one job per recipient, with a configurable rate so a large list doesn't burn the IP reputation (ties in with the blocklist checks above and the IP warm-up); show per-campaign progress and results in the admin UI. Document the endpoints, the public unsubscribe flow and any new env vars in `apps/docs`.
