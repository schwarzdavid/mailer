# schwarzdavid Mailer

> **Work in progress.** This project is under development. Features, APIs and the database schema can still change without notice, and it is not ready for production use yet.

## About

schwarzdavid Mailer is a self-hosted mail service. It lets websites send email reliably without needing a backend of their own. It has two parts: an admin web app where everything is configured, and a public HTTP API that websites send requests to.

What works so far:

- **Inbound forms.** You define a form with its fields, security checks (reCAPTCHA, CSRF, honeypot) and receivers. A static website can then POST its contact form straight to a public endpoint. Each accepted submission goes out to the receivers as a DKIM-signed email, rendered from a versioned Handlebars template. The template editor has a live preview.
- **Domains & DNS.** You register sending domains, the service generates DKIM keys for them, and it lists the DNS records each domain needs (SPF, DKIM, DMARC, MX, A/AAAA, PTR). A scheduled job checks those records regularly and reports their health.
- **Platform sending domain.** You configure the service's own infrastructure domain once, in the settings or during first-start onboarding. It is used as the SPF include and as the bounce (return-path) domain.
- **Bounce handling.** A dedicated bounce mailbox is polled over IMAP, and SMTP 5xx rejections are recorded at send time. Recipients that bounce permanently, or bounce temporarily too often, are blocked automatically. Admins can review and lift blocks in the UI.
- **Projects.** Projects group inbound forms and the domains assigned to them.
- **Users & permissions.** Users have roles (Super Admin, Admin, User), optional direct permission grants and per-project memberships. Access checks use CASL on both the backend and the frontend.

### Tech stack

A pnpm + Turborepo monorepo:

| Workspace       | Stack                                                                                           |
| --------------- | ----------------------------------------------------------------------------------------------- |
| `apps/backend`  | NestJS, Sequelize/PostgreSQL, Redis, Passport JWT, Nodemailer, ImapFlow                         |
| `apps/frontend` | Vue 3, Vuetify, Vue Router, TanStack Query, vue-i18n, vee-validate + Zod                        |
| `packages/api`  | Typed client and Zod schemas generated by `@hey-api/openapi-ts` from the backend's OpenAPI spec |

## Local setup

### Prerequisites

- Node.js `^22.18.0` or `>=24.12.0`
- pnpm (the exact version is pinned in `package.json` under `packageManager`; `corepack enable` picks it up)
- Docker with Docker Compose

### 1. Install dependencies

```bash
pnpm install
```

### 2. Configure the environment

Copy the template to a root `.env`. The defaults already match the local Docker services.

```bash
cp .env.example .env
```

Change `BACKEND_JWT_SECRET` and `BACKEND_DKIM_SECRET` to any non-trivial values. The DKIM secret encrypts the stored private keys, so if you change it later, existing keys can no longer be decrypted.

### 3. Start the infrastructure

```bash
docker compose -f dev/docker-compose.yml up -d
```

| Service    | Purpose                   | Ports                                           |
| ---------- | ------------------------- | ----------------------------------------------- |
| PostgreSQL | Main database             | `5432`                                          |
| Redis      | Cache                     | `6379`                                          |
| MailHog    | Catches all outgoing mail | SMTP `1025`, web UI http://localhost:8025       |
| GreenMail  | Bounce mailbox            | SMTP `3025` (inject DSNs), IMAP `3143` (polled) |

### 4. Run the database migrations

```bash
pnpm --filter backend migrate up
```

### 5. Generate the API client

The OpenAPI spec and the generated client are not committed, so you have to create them once (and again after every API change). Generating the spec boots the backend, so Postgres and Redis must already be running.

```bash
pnpm --filter backend generate
pnpm --filter api build
```

### 6. Start the apps

```bash
pnpm dev
```

- Frontend: http://localhost:5173 (proxies `/api` to the backend)
- Backend API: http://localhost:8000/api
- Swagger UI: http://localhost:8000/docs

On first start the frontend sends you to the onboarding wizard. There you create the first (Super Admin) user and configure the platform sending domain. Locally, the DNS records will stay "pending", which is expected.

### Useful commands

```bash
pnpm lint                         # ESLint (+ oxlint in the frontend)
pnpm typecheck                    # tsc / vue-tsc
pnpm test                         # unit tests across all workspaces
pnpm --filter backend test:e2e    # backend e2e tests (needs Docker, uses Testcontainers)
pnpm check                        # lint + typecheck + test + format check
```

## Open todos

- [ ] **Dashboard** The dashboard is still an empty placeholder.
- [ ] **UI** The current UI is only as meant as a proof of concept and needs to be improved/rewritten.
- [ ] **Public send API** Let customers send email through an API-key-authenticated endpoint. The mail module is already built for this.
- [ ] **Role editor** The schema supports custom roles, but only the three seeded roles exist so far. There are no endpoints or UI to create, edit or delete roles.
- [ ] **Encrypt security secrets** reCAPTCHA secrets on inbound forms are stored in plain text. They should be encrypted like DKIM keys.
- [ ] **Bounce improvements:**
    - [ ] VERP / per-delivery return paths, so bounces can be linked back to the inbound form delivery that caused them
    - [ ] Pagination for the bounce log
    - [ ] Automatic purge of old bounce rows
    - [ ] An e2e test suite for the bounce module
- [ ] **Transactional domain creation** Creating a domain or the sending domain takes several steps that do not yet run in a single transaction.
- [ ] **Branding settings** Customization options such as colors and a logo on the settings screen and in onboarding.
- [ ] **Production deployment** Dockerfiles, a production compose/deployment setup and deployment documentation.
- [ ] **CI pipeline** Run `pnpm check` and the e2e suite automatically on every push.
