# mailer CLI: guided setup, updates and auto-update

Date: 2026-11-26
Status: draft, awaiting owner approval

## Intent

mailer is installed on a single VPS by freelancers and small to mid-sized agencies. Today the installation is a list of manual steps (copy three files, fill `.env`, run `setup.sh`), and an update is a longer list (download the new files, diff `.env`, pin the tag, pull, restart, know how to roll back). The steps put people off, and because an update needs a person, updates do not get installed.

The goal is one small host script, `mailer.sh`, that pulls the mailer image and runs an interactive Node CLI inside it with the install directory mounted. The CLI guides the operator through the setup and writes every file. The same script starts and stops the stack, updates it to a newer version, and can install an unattended auto-update. The admin UI knows which version runs and tells the operator about new or automatically installed versions.

## Goals

- A fresh server reaches a running mailer with one download and one command, answering a handful of questions.
- Updating is one command, or none with auto-update.
- From the first release of this work on, every newer image can take over every older install directory without manual steps.
- Secrets are generated by default; a secret manager is possible and never required.
- A failed update never leaves the site down unattended when the previous version can be put back.

## Non-goals

- Native secret-manager integrations (Vault, 1Password, … SDKs) in the backend or the CLI.
- Docker `_FILE` secrets.
- Client-side encrypted backups, and backup storage that does not speak the S3 API.
- Triggering an update from the admin UI.
- Multi-node, Swarm, Kubernetes, Windows or macOS hosts.

## Anti-goals

- No container ever gets the Docker socket.
- No secret value in a log, a backup archive or the process list.
- No update that requires reading release notes to succeed.

## Constraints

- A container cannot run `docker compose` on the host without the Docker socket. So the container only reads and writes files in the mounted directory, and `mailer.sh` runs every Docker command.
- Operators edit `compose.yml` today (external Postgres, for example). A CLI that regenerates the file would destroy those edits.
- The image runs as `node` (uid 1000) with a read-only root; the install directory usually belongs to `root`.
- The smoke test drives the setup script non-interactively, from Git Bash on Windows.
- A failed migration rolls back its whole run and keeps the backend from starting. That stays.

## Approaches

1. **CLI inside the mailer image (chosen).** One artifact and one release. The CLI of a version knows exactly its own compose file and its own host script, and migrates older install directories forward.
2. **A separate `mailer-cli` image.** Smaller and independently releasable, but a second artifact and a compatibility matrix between CLI and app versions, which is the burden this work is meant to remove.
3. **Everything in POSIX shell.** No container, but interactive guidance and file migrations in `sh` are error-prone and hard to test, and the owner asked for a Node CLI.

The owner picked 1.

For secrets, three levels were considered: generated into `.env` (default), a tool-neutral wrapper command for secret managers (optional), and native provider integrations (rejected, see non-goals). The owner confirmed that a secret manager must stay optional.

For the auto-update trigger, a host timer was chosen over an updater container, because the container would need the Docker socket.

## Design

### The install directory

```
/opt/mailer/
  mailer.sh               host launcher; owned by the CLI, replaced on update
  compose.yml             owned by the CLI, replaced on update; never edited by hand
  compose.override.yml    optional, owned by the operator; never touched
  .env                    settings, launcher state and (by default) secrets; the CLI changes only keys it knows
  state/                  written by the launcher, mounted read-only into the backend
  backups/                dumps and pre-update snapshots
```

- `compose.yml` stays a plain file driven by `.env` interpolation, as today. `deploy/compose.yml` remains its single source; the image carries a copy and the CLI writes it out unchanged.
- Operator changes move to `compose.override.yml`, which Compose loads automatically. Every compose edit the docs describe today must be expressible there; where it is not, the builder adds an `.env` switch instead.
- `.env` is the only settings file. Besides the backend's settings it holds the launcher's own keys under the prefix `MAILER_`: the format version (an integer, starting at 1), the secret wrapper command, the auto-update settings, the backup storage settings and the previous image tag. The launcher reads them without Node. The pinned version stays `IMAGE_TAG`, which is never `latest` after setup. A second file for launcher state was considered and dropped: one file is less to explain and to keep safe. Its price is that the backend also receives the `MAILER_` keys through `env_file`, including the storage credentials, which it ignores.

### Launcher and image: the frozen contract

`mailer.sh` is POSIX `sh`. It needs Docker with Compose and nothing else. Two kinds of commands:

- **Host-only**, thin wrappers around Compose that start no container: `start`, `stop`, `restart`, `status`, `logs [service]`, `compose <args…>` (pass-through), `token` (prints the setup token), `version`.
- **Container-backed**: `setup`, `update`, `rollback`, `backup`, `restore`, `autoupdate enable|disable|status`, `recovery-kit`, `doctor`.

The launcher calls the CLI as:

```
docker run --rm [-it] --user "$(id -u):$(id -g)" -e HOME=/tmp \
    -v "$DIR:/project" ghcr.io/schwarzdavid/mailer:<tag> mailer <command> [args]
```

`mailer` is an executable on the image's `PATH`. The image also carries `mailer.sh` and `compose.yml`; today `.dockerignore` excludes `deploy` and the image holds only the backend's deploy output, so both change and `deploy/` becomes a build input. Commands that need secrets under a secret-manager wrapper (`setup`, `recovery-kit`) add name-only `-e KEY` flags.

An old launcher must be able to hand over to any newer image, and it must do so before any host-side step, so that every safety step of an update comes from the new version. The part that may never change is therefore kept minimal. To update, an old launcher does exactly this:

1. pull the target image and run `mailer migrate-project [--dry-run]` in it, with the `docker run` form above and the `/project` mount,
2. on success, `exec sh ./mailer.sh _finish-update <from> <to>`.

`migrate-project` is non-interactive and idempotent. It takes the update lock (a lock directory in the project, which `_finish-update` releases), copies `compose.yml`, `.env` and `mailer.sh` into a snapshot, and then brings the directory to this image's format: a new `compose.yml`, a new `mailer.sh` (written to a temporary file and renamed, so the running shell is not corrupted), new `.env` keys and the new `IMAGE_TAG`. Exit code 0 = done; a dedicated non-zero code = "needs manual action" with a message on stderr and nothing changed. The old containers keep running until `_finish-update` replaces them.

Everything else (command names, prompts, the `MAILER_` keys, the snapshot layout, the `state/` files) may change between releases, because the lock, the snapshot and every host-side step are written and read by the same version.

### Project migrations

`migrate-project` works like the database migrations: a numbered chain of steps from format N to N+1, so an image migrates a directory of any older format in one run, with no need to step through intermediate releases. The repository keeps one fixture directory per released format, and a test migrates every fixture to the current format.

Format 0 is the hand-made layout of today (`compose.yml`, `.env`, `setup.sh`), as shipped by the existing tags `v0.0.1`, `0.0.2` and `v0.0.3` to `v0.0.5`. Adopting it is interactive only (`mailer.sh setup` in that directory): a `compose.yml` that differs from every released template is kept as `compose.yml.legacy`, and the operator is told to move the differences to `compose.override.yml`. Auto-update is only available from format 1.

### Setup

Bootstrap, the only manual download:

```
mkdir -p /opt/mailer && cd /opt/mailer
curl -fsSLO https://github.com/schwarzdavid/mailer/releases/latest/download/mailer.sh
sh mailer.sh setup
```

The release pipeline attaches `mailer.sh` to every release. In an empty directory the launcher runs the wizard from the `latest` image, and the wizard pins its own version.

The wizard asks for:

- `SITE_ADDRESS` and `MAIL_HOSTNAME` (must differ; the existing warning about the registrable domain is shown),
- `MAIL_SERVER_IPV4` and the optional `MAIL_SERVER_IPV6`, offering the addresses that `MAIL_HOSTNAME` resolves to as defaults, and warning when a name does not resolve yet,
- how to handle the four secrets (`DB_PASSWORD`, `BACKEND_JWT_SECRET`, `BACKEND_ENCRYPTION_SECRET`, `MAIL_PASSWORD`): generate them (default), type them in (the two backend secrets need at least 32 characters), or use a secret manager,
- whether to enable auto-update (default yes).

It then writes the files, and the launcher does the host part that `setup.sh` does today: check the Compose version, `up -d`, wait for `mail`, create or re-password the bounce mailbox and the `postmaster` alias, print the URL and the setup token.

Rules:

- Every prompt has a flag or an `.env` value that answers it, and `--yes` accepts all defaults. With a filled `.env`, setup asks nothing. The smoke test uses this. A setup that asks nothing never installs the auto-update timer unless a flag asks for it, and re-runs and the adoption of format 0 leave the timer as it is.
- The mail password reaches docker-mailserver through stdin or a file, never as a command argument (`setup.sh` passes it as an argument today, which shows it in the process list).
- Running `setup` again shows the current values as defaults and is always safe. It never overwrites a set secret, and it refuses to change `BACKEND_ENCRYPTION_SECRET`.
- At the end it prints the recovery kit: site, mail hostname, version, the four secrets and the fingerprint of the encryption secret, with the request to store it in a password manager. `mailer.sh recovery-kit` prints it again. It is not written to an extra file.

### Secrets

- **Default:** values in `.env`, mode 0600.
- **Secret manager (optional):** the operator gives a wrapper command, stored in `.env`, for example `op run --env-file=secrets.env --`, `infisical run --`, `doppler run --` or `sops exec-env secrets.enc.env '{}'`. Most tools take the command as a suffix; some take it as one quoted argument, so the setting supports a placeholder for the command. The launcher re-executes itself under that command, so the secrets exist as environment variables for the launcher and for Compose and are not in `.env`. `compose.yml` therefore passes the four secrets to the services through `environment:` interpolation (shell environment wins over `.env`), where the backend gets its two secrets only through `env_file` today, and the launcher reads `MAIL_PASSWORD` from the environment before `.env`. In this mode the wizard can still generate the values and show them once, for the operator to store in the manager. `doctor` and every start fail with a clear message when a secret is missing under the wrapper.
- Unattended auto-update with a wrapper needs a wrapper that works without a person (a service-account token). `autoupdate enable` checks this once.

### Update

`mailer.sh update [major] [--to <version>] [--auto]`:

1. Find the target: `--to`, or `mailer resolve-update` from the current image, which reads the GitHub releases and returns the newest stable release of the running major, or of any major with `major` (see Auto-update). With `--auto` the release must also be at least 3 days old; the number of days is a setting. No target: exit 0.
2. Pull the target image and run its `migrate-project`, which locks, snapshots and migrates the files. "Needs manual action" stops here, with nothing changed.
3. Hand over to the new launcher's `_finish-update`. With the old containers still running, it records the applied database migrations and takes a database dump into `backups/` (the last 3 pre-update dumps are kept). Then `pull`, `up -d --remove-orphans --wait`, mailbox check.
4. The update succeeded when the backend container is healthy, which is the liveness check. Readiness is not the criterion: it also fails when `mail` is down for reasons unrelated to the update, such as a certificate or DNS problem.
5. On failure, roll back automatically: revert database migrations that the new version applied (with the new image's migration CLI, down to the recorded one; a failed migration run has already rolled itself back), restore the snapshot, start the previous version. The new version never served a request at this point, so reverting its migrations loses no data.
6. Write the result (from, to, time, automatic or not, ok / rolled back / needs manual action) to `state/` and release the lock.

If the rollback itself fails, the launcher stops, leaves the dump and the snapshot in place and says so in `state/` and on stderr.

`mailer.sh rollback`, run by hand after a successful update, is different: reverting migrations then deletes whatever the new version wrote to new tables and columns. It takes a dump first, names that loss and asks for confirmation; it never runs unattended.

A release counts as available only once `mailer.sh` is attached to it. The pipeline attaches it as its last step, after the image is pushed, so neither `resolve-update` nor the UI notice ever names a release whose image does not exist, and the owner keeps publishing releases as today.

### Auto-update

`mailer.sh autoupdate enable` installs a daily systemd timer with a random delay that runs `mailer.sh update --auto`, or a cron entry where there is no systemd. `disable` removes it, `status` shows the timer and the last result. It needs root, like the installation.

Auto-update stays inside the running major version: minor and patch releases install unattended, a new major does not. A migration can convert the installation, but not the websites that call the send API, post to the form endpoints or embed a pinned client version, and those must not break overnight without anyone having acted. There is no setting that lets auto-update cross a major.

A plain `mailer.sh update` stays inside the running major as well: it installs the newest minor or patch release, and when a newer major exists it prints a notice that names the version, the release notes and the command to install it. Only `mailer.sh update major` crosses a major. It goes straight to the newest stable release and migrates everything itself as for any other release, so the rule below holds for majors too. Typing the command is the confirmation; it asks nothing further. `--to <version>` with a version of another major is refused in the same way unless `major` is given.

Whether an older major line keeps receiving fixes is undecided, and nothing in the CLI, the UI or the docs promises or denies it: no end-of-support notice, no escalating warning.

Inside a major, a release whose migration cannot be automated reports "needs manual action", auto-update stops at the version before it, and the admin UI says so.

### Backup and restore

- `mailer.sh backup` writes a `pg_dump` custom-format dump and a small metadata file next to it: mailer version, last applied migration and the fingerprint of `BACKEND_ENCRYPTION_SECRET` (a keyed hash computed in the backend container, never the secret). Secrets are not part of a backup; the recovery kit is their backup, kept somewhere else. The command reminds the operator of that.
- `mailer.sh restore <dump>` refuses when the fingerprint in the metadata differs from the current secret, and refuses when the database is not empty. `--replace` lifts the second refusal: it dumps the current database, asks for confirmation, and replaces it. The restore runs with the backend stopped, then the stack starts as `setup` does.
- **Off-site storage (optional).** A dump on the server's own disk does not survive the loss of that server, so backups can go to a bucket. `mailer.sh backup storage` asks for endpoint, region, bucket, an optional prefix and an access key pair, checks them with a test object and stores them in `.env` (or leaves the key pair to the secret manager). It speaks the S3 API only, which covers AWS S3, Google Cloud Storage (interoperability mode with HMAC keys), Cloudflare R2, Backblaze B2, Hetzner Object Storage and MinIO. With storage configured, every `backup` and every pre-update dump is uploaded together with its metadata file by the CLI in the container, and a failed upload makes the command fail while the local dump stays.
- `mailer.sh backup list` shows local and remote backups; `mailer.sh restore` takes a local file or the name of a remote backup, which it downloads first. On a new server the order is `setup` with the secrets from the recovery kit, `backup storage`, `restore`.
- `mailer.sh backup schedule enable|disable|status` installs a nightly timer the same way as the auto-update; the wizard offers it. Retention is a number of backups to keep (default 14), applied locally and in the bucket.
- A backup still carries no secrets, so a leaked bucket exposes no DKIM key and no reCAPTCHA secret. It does hold everything else in the database, including addresses and password hashes; the docs tell the operator to keep the bucket private and to turn on the provider's encryption at rest.
- The docs' nightly cron line is replaced by the schedule.

### Version awareness in the admin UI

- The release pipeline bakes the release version into the image. The backend exposes it, together with the newest stable release, the release-notes URL (`https://github.com/schwarzdavid/mailer/releases/tag/v<version>`), whether auto-update is on and the last update result from `state/`, on one authenticated endpoint.
- A daily single-instance job asks the GitHub releases API for the newest stable release and caches the answer. `UPDATE_CHECK_ENABLED=false` turns it off; a failed check is silent.
- The UI shows the running version, and to users who may see the settings: "version X is available" with the changelog link and the command to run, which for a new major is `mailer.sh update major` and also says that auto-update does not install it and that the release notes name what changes for embedding websites; "updated to X on <date>" (automatically or by hand) with the changelog link, dismissible per version; and a warning when an automatic update was rolled back or needs manual action.
- The inbound-form snippet pins the jsDelivr URL to the running release version (`…/mailer-client@<version>/dist/client.iife.js`), and stays unpinned on a build that is not a release. For this the pipeline publishes the npm package before it pushes the image, so a released image never names a version npm does not have. Today `npm-publish` needs the `image` job, which builds, smoke-tests and pushes in one go; the job is split into build and smoke test, then npm publish, then image push, then the `mailer.sh` asset. An npm version whose image push fails afterwards stays published and is harmless.

### The rule for future changes

Added to `CLAUDE.md` with the implementation: any change that could break an existing installation (the compose file, an environment variable, a volume, a host-side step, the launcher contract, the `state/` files, the database) ships in the same change with a project or database migration that the auto-update applies unattended, a fixture for the old format, and a test that migrates it. If a change truly cannot be automated, it must make `migrate-project` report "needs manual action" instead of failing later, and the docs name the manual steps.

## Delivery order

Three projects, planned and built one after the other:

1. **CLI, launcher and project format**: `mailer.sh` replaces `setup.sh`; wizard, secrets handling, recovery kit, host-only commands, the frozen contract with `migrate-project` and a plain manual `update`, adoption of format 0, docs and smoke test.
2. **Safe updates**: pre-update dump, rollback, `backup`/`restore` with S3-compatible storage and the nightly schedule, `resolve-update`, auto-update timer, `state/`.
3. **Version awareness**: version endpoint, update check, UI notices, pinned jsDelivr URL, pipeline order.

The manual `update` is part of project 1 on purpose: the first released launcher must already be able to hand over to a newer image. Because the hand-over happens before any host-side step, an update from a project-1 installation to a project-2 release already gets the dump and the rollback of project 2.

## Calls made by the author, not yet confirmed by the owner

- Operator edits live in `compose.override.yml`; `compose.yml` is never edited by hand any more.
- Auto-update defaults to "yes" in the wizard and waits 3 days after a release. (Staying inside the major, with `update major` as the only way across, is the owner's decision.)
- The CLI is its own private workspace, bundled into the image as the `mailer` executable, so its prompt library does not become a backend dependency.
- Release information comes from the GitHub releases API, for the launcher and for the backend.
- The backend learns about update results from a read-only bind mount of `state/`, not from an API the launcher would have to authenticate against.
- Backups carry no secrets and are not encrypted by the CLI; the bucket's own encryption is the protection at rest.
- Backup retention defaults to 14, locally and in the bucket.
- An old launcher hands over to the new one before any host-side step; the new version snapshots, dumps and rolls back.
- An update counts as successful on backend liveness, not readiness.
- An automatic rollback reverts the new version's migrations without asking; a manual `rollback` dumps and asks first.
- A release becomes visible to updates when `mailer.sh` is attached to it; the release flow stays as it is, and the pipeline order changes to npm before image.
- An unattended setup does not install the auto-update timer unless a flag asks for it.
- `restore` refuses a non-empty database unless `--replace` is given.
- Installations in today's layout are adopted interactively; they get auto-update only afterwards.

## Left to the builder

- The prompt library, the CLI's internal structure and the exact names of flags and `MAILER_` keys, and the S3 client (a small one; the full AWS SDK is not needed).
- The file format inside `state/` and the shape of the version endpoint.
- How the launcher locks, and how it names the timer when several installations share a host.
- How the smoke test fakes the release list (an override of the releases URL is expected).
- Which docs pages are split or merged; every page that names `setup.sh` changes.
