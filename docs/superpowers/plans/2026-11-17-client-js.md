# client-js Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A typed, zero-dependency JavaScript/TypeScript client `@schwarzdavid/mailer-client` (folder `packages/client-js`) for the public form and send endpoints, published to npm, whose IIFE build replaces the backend's hand-serialised `client.js`.

**Architecture:** One ESM package with the entry points `.`, `./forms` and `./send`, plus an IIFE bundle `./client.iife.js` that the backend reads once at startup and serves at `GET /api/v1/forms/client.js`. The client is hand-written on `fetch`; a type-level test pins its request/response types to the generated `api` package so backend contract changes break the build. A GitHub release publishes the package to npmjs with the release's version.

**Tech Stack:** TypeScript (strict, repo `tsconfig.json`), tsdown (ESM + bundled `.d.ts` + IIFE), Vitest, ESLint flat config via `defineBaseConfig`, Turborepo, pnpm workspaces, NestJS (backend), Vue 3 (admin UI snippets), VitePress (docs), GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-17-client-js-design.md`

## Global Constraints

- Never touch git: no `git add`, commit, push or other version-control change. Every task ends with "no commit"; the owner commits.
- No code comments (CLAUDE.md working agreement). Plain, comment-free JSON configs.
- Every task keeps `pnpm lint` and `pnpm typecheck` green for the packages it touches; run the package tests it touches.
- npm name `@schwarzdavid/mailer-client`; folder `packages/client-js`; the workspace `name` is the npm name.
- Licence of the package: MIT (own `LICENSE` file, `"license": "MIT"`); everything else stays `AGPL-3.0-only`.
- Zero runtime dependencies; only the platform `fetch`, `AbortSignal.timeout`, `URL`. ESM only, `sideEffects: false`, target ES2022, `engines.node: ">=20"`.
- `api` is a **devDependency** of the client only; nothing in `dist/` may import `api`.
- Requests to form endpoints use `credentials: 'omit'`. The send client sends `Authorization: Bearer <apiKey>` and never `?key=`.
- `MailerError.retryable` is `true` exactly for status `0` (network/timeout), `429`, `502`, `503`.
- Option name for the browser override: `dangerouslyAllowBrowser`.
- Token automation in `MailerForm` is on only when `timedToken` is given; the token is never fetched in the constructor.
- Prettier formats everything (`pnpm format:fix`); 4 spaces, single quotes, no semicolons.

## Review Focus

1. `baseUrl` with a trailing slash, with a sub-path (`https://host/mailer`), or not absolute: trailing slashes are dropped, the sub-path is kept, a non-absolute value throws a `TypeError` in the constructor, not on the first request. → Task 1, `resolveApiBase` tests.
2. Error answers whose body is not JSON (`413` from the proxy, an HTML `502` page): `MailerError` keeps the status, `messages` is `[]`, nothing throws a `SyntaxError`. → Task 1, `request` tests.
3. A double click on submit: two concurrent `MailerForm.submit` calls must not send the same token twice. → Task 3, "concurrent submits use different tokens".
4. `prepare()` whose token request fails (429, network): no unhandled rejection; the next `submit` requests again and rejects with that `MailerError`. → Task 3, "a failed prepare surfaces on submit".
5. A small `timeoutMs` and a token with a longer `waitMs`: the local wait does not count towards the request timeout. → Task 2, "the timeout does not cover the token wait".

### Task 3: `MailerForm`

**Files:**

- Create: `packages/client-js/src/forms/mailer-form.ts`; export from `src/forms/index.ts`
- Test: `packages/client-js/src/forms/mailer-form.spec.ts`

**Interfaces:**

- Consumes: `createFormClient` and its `issueToken`, form types (Task 2)
- Produces:
    - `interface MailerFormOptions extends ClientOptions { formKey: string; timedToken?: TimedTokenPlacement }`
    - `class MailerForm<TData extends FormValues = FormValues, TSecurity extends FormValues = FormValues>` with `constructor(options: MailerFormOptions)` (validates `baseUrl` via `resolveApiBase`, makes no request), `readonly formKey: string`, `prepare(): void`, `submit(submission: FormSubmission<TData, TSecurity>): Promise<FormSubmitResult>`

Behaviour (spec, "Forms"):

- Without `timedToken`: `prepare()` does nothing; `submit` is the low-level submit.
- With `timedToken`: `prepare()` starts `issueToken` if no usable token is cached; it never rejects (attach a handler that drops the cache on failure). `submit` takes the cached token request or starts one, awaits it, **removes it from the cache before sending** (so a concurrent submit fetches its own), places the token under `timedToken.key` in `security` (body), `headers` (header) or `query` (query), replacing a caller value under the same key, and sends. On a `400` answer it puts the token back into the cache if the cache is still empty; on any other answer or error it stays dropped.
- A cached token is unusable once `Date.now() > receivedAt + waitMs + (expiresAt − notBefore) − 5000` (local clock only, so client/server clock skew does not matter); `prepare` and `submit` then fetch a new one.

- [ ] **Step 1: Write the failing tests** (fake timers, stub `fetch` answering token and submit routes):
    - "does not request a token in the constructor".
    - "without timedToken submits without any token request".
    - "prepare fetches once and submit reuses that token": `prepare(); prepare();` → one token request; `submit` sends that token and makes no second token request.
    - "submit fetches the token itself when prepare was not called" and resolves only after `waitMs`.
    - "places the token in the body/header/query": three cases with `location` `'body'` (`security.formToken`), `'header'` (`headers['x-form-token']`), `'query'` (`?formToken=`).
    - "replaces a caller value under the token key".
    - "drops the token after 202 and 403, keeps it after 400": after 400 the next submit sends the same token without a token request; after 202/403 it requests a new one.
    - Review Focus 3 — "concurrent submits use different tokens": two `submit` calls without awaiting → two token requests, two different tokens sent.
    - Review Focus 4 — "a failed prepare surfaces on submit": token route answers 429 on the first call; `prepare()` causes no unhandled rejection (`process.on('unhandledRejection')` spy stays uncalled after flushing); the following `submit` requests again and, if that also answers 429, rejects with `MailerError` `status: 429`, `retryable: true`.
    - "replaces an expired cached token": token `notBefore`/`expiresAt` 60 s apart, `waitMs` 1000; advance time 57 s after receipt → `submit` requests a new token.
    - "submit rejects with the submit error": 404 → `MailerError` status 404.
